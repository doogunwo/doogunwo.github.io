해시 함수를 빠르게 계산한다고 해서 해시 테이블 조회까지 빨라지는 것은 아니다. 키가 어느 위치에서 탐색을 시작하는지, 충돌한 항목을 어떻게 배치하는지, 실제로 몇 개의 슬롯과 문자열을 확인하는지가 함께 작용한다. 로그용 키를 처리하는 SHashTable을 살펴보면서 확인하고 싶었던 것도 이 관계였다. 해시 출력이 고르게 분산되는지를 먼저 보고, 그 특성이 실제 삽입과 조회에서도 어떻게 나타나는지 측정했다.

이 글은 `shashtable`의 `shash.c`, `hashtable.c`와 두 헤더에 구현된 구조를 기준으로 설명한다. 측정값은 별도로 수행한 해시 함수 평가와 Robin Hood 테이블 평가 자료에서 가져왔다. 중심 비교 대상은 64바이트 키를 처리하는 SipHash 기반 logging 경로와 Linux의 `jhash`이며, 두 함수를 **같은 SHashTable에 적용했을 때**의 차이를 살펴본다.

## 해시 함수와 해시 테이블을 구분하기

SHashTable은 키를 해시값으로 바꾸는 함수만을 뜻하지 않는다. 저장 공간을 확보하고, 충돌을 처리하고, 항목을 삭제하거나 테이블 크기를 바꾸는 기능까지 포함한다. 이 가운데 기본 해시 경로는 SipHash-1-4를 사용하고, 충돌 처리는 Robin Hood 방식의 선형 탐색으로 구현했다. 따라서 해시 함수 평가와 테이블 평가는 서로 다른 질문에 답한다. 전자는 입력을 얼마나 고르게 분산시키고 얼마나 빨리 계산하는지, 후자는 그렇게 얻은 시작 위치에서 실제 항목을 찾는 데 얼마나 많은 작업이 필요한지를 본다.

외부 사용자는 `shash.h`의 생성·삽입·조회·삭제 API를 호출한다. 내부 레이아웃은 `hashtable.h`에 있고, 해싱과 탐색·재배치 로직은 `hashtable.c`에 모여 있다. `shash.c`는 공개 API와 해시 콜백 선택, 참조 관리 등을 연결한다. 전체 조회 흐름을 줄이면 다음과 같다.

```text
key
  -> hash function
  -> 32-bit hash
  -> home bucket = hash & mask
  -> metadata probe
  -> key equality check
  -> value
```

### 메타데이터와 key/value 배열

탐색에 필요한 정보와 실제 key/value 포인터는 별도의 배열에 저장한다. 같은 인덱스의 `meta[i]`와 `entries[i]`가 하나의 항목을 구성한다.

```c
typedef struct {
    guint32 hash;
    guint32 psl;
} SHashMeta;

typedef struct {
    gpointer key;
    gpointer value;
} SHashEntry;
```

조회는 먼저 `meta[]`의 해시값과 PSL을 확인하고, 저장된 해시가 일치할 때 `entries[]`의 키를 비교한다. 즉 탐색한 모든 슬롯에서 문자열 비교를 수행하는 구조는 아니다. 배열 분리는 이 접근 순서를 구현한 것이며, 이번 실험은 배열을 합친 구현과 비교하지 않았으므로 분리 자체의 성능 이득은 별도로 산정하지 않는다.

키와 값은 포인터로 보관하며 테이블이 자동으로 복사하지 않는다. 삭제 시 해제 여부는 생성할 때 지정한 destroy callback이 결정한다. 또한 참조 카운트에 원자 연산을 사용한다고 해서 삽입과 조회 전체가 동시 접근에 안전해지는 것은 아니다. 테이블 연산의 동기화와 객체의 참조 수 관리는 구분해야 한다.

## 64바이트 로그 키를 해싱하는 경로

logging 경로는 이미 만들어진 SHA-256 hex 문자열의 64바이트를 입력으로 받는다. 여기서 SHA-256을 다시 계산하는 것은 아니다. `s_logging_hash()`는 입력 길이를 64로 고정하고 SipHash-1-4를 호출한다. 반면 일반 문자열 경로인 `s_str_hash()`는 `strlen()`으로 길이를 구한 뒤 같은 코어를 사용한다. 고정 길이 경로를 사용하려면 실제 입력 버퍼에 읽을 수 있는 64바이트가 있어야 한다.

테이블에는 128비트 시드가 저장된다. SipHash 코어는 64비트 값을 만들고, 구현은 그 상위·하위 32비트를 XOR해 테이블에서 사용할 32비트 해시값을 얻는다. 빈 슬롯을 해시값 0으로 표시하므로 결과가 0이면 2로 정규화한다.

```c
hash64 = s_siphash14_core(table, key, length);
hash32 = (guint32)(hash64 ^ (hash64 >> 32));
hash32 = s_normalize_hash(hash32);
```

함수 이름만 보고 실제 사용 경로를 판단하면 한 가지를 놓치기 쉽다. `s_str_key_hash()`를 직접 호출하면 DJB2 계열 계산을 하지만, 그 함수를 테이블 생성자의 콜백으로 전달하면 내부 선택 로직이 `s_str_hash()`로 바꾼다. 따라서 실험에서 `legacy`라고 부른 직접 호출 결과는 현재 테이블의 일반 문자열 경로 성능이 아니다.

| 실험 이름 | 실제 측정 대상 | 입력 처리 |
| --- | --- | --- |
| logging | `s_logging_hash()` | 고정 64바이트, SipHash-1-4 |
| string | `s_str_hash()` | `strlen()` 포함, SipHash-1-4 |
| legacy | `s_str_key_hash()` 직접 호출 후 정규화 | DJB2 계열 |
| jhash | Linux `jhash()` 후 정규화 | 명시적 길이 입력 |

`jhash`는 사용자 공간에서 컴파일한 커널 헤더의 함수를 사용했다. 이 비교는 Linux 커널 내부의 실행 성능이나 커널 해시 테이블 전체와의 비교가 아니다.

## Robin Hood는 충돌 이후의 거리를 관리한다

해시값이 정해져도 곧바로 저장 위치가 확정되는 것은 아니다. 테이블 용량은 2의 거듭제곱이고, `hash & mask`로 시작 위치인 home bucket을 구한다. 그 위치가 차 있으면 다음 슬롯으로 이동하며, 원래 위치에서 얼마나 밀려났는지를 PSL에 기록한다. 시작 버킷이 같은 키뿐 아니라 서로 다른 시작 위치에서 출발한 키의 탐색 경로도 겹칠 수 있다.

삽입에서는 현재 들어갈 항목의 PSL이 기존 항목의 PSL보다 크면 둘을 교환한다. 더 멀리 이동한 항목을 그 자리에 두고, 밀려난 기존 항목이 다음 슬롯에서 탐색을 계속한다. 예를 들어 들어갈 항목의 PSL이 3이고 해당 슬롯의 항목은 PSL이 1이라면, 새 항목이 자리를 차지한다. 교환은 메타데이터와 key/value 쌍에 함께 적용된다.

이 배치 규칙은 실패 조회를 끝내는 조건으로도 쓰인다. 빈 슬롯을 만나면 찾는 키가 없고, 현재 탐색 거리가 저장된 항목의 PSL보다 커져도 조회를 끝낼 수 있다. 해당 키가 있었다면 Robin Hood 삽입 규칙에 따라 그 위치를 지나오기 전에 배치되었어야 하기 때문이다. 구현의 핵심 조건은 다음과 같다.

```c
if (meta->hash == 0U)
    return FALSE;

if (current_psl > meta->psl)
    return FALSE;
```

삭제할 때는 중간 슬롯을 비워 놓기만 해서는 안 된다. 뒤에 밀려 있는 키를 찾는 조회가 그 빈자리에서 잘못 종료될 수 있기 때문이다. 구현은 뒤 항목을 한 칸씩 당기면서 PSL을 줄이는 backward-shift 방식을 사용한다. 다음 슬롯이 비어 있거나 PSL이 0인 항목을 만나면 이동을 끝낸다. 리사이징에서는 저장된 해시값을 재사용해 새 용량에 맞게 항목을 재배치한다. 확장 판단 기준은 75% 점유율이며, 축소 판단 기준은 25%이다.

## 비트 확산과 충돌은 서로 다른 특성이다

해시 품질은 입력 한 비트를 바꿨을 때 출력이 어떻게 달라지는지부터 확인했다. 32비트 출력의 각 비트가 절반의 확률로 바뀐다면 평균 변경 비트 수는 16이다. 다만 평균만으로는 특정 입력 비트와 출력 비트 사이의 편향을 놓칠 수 있어, SAC(Strict Avalanche Criterion) 평가에서 비트 쌍별 변화 확률이 0.5에서 얼마나 벗어나는지도 측정했다.

| 64바이트 입력 | 평균 변경 비트 | SAC 최대 편향 | SAC RMS 편향 |
| --- | ---: | ---: | ---: |
| logging | 16.0009 | 0.0197 | 0.00500 |
| string | 16.0009 | 0.0197 | 0.00500 |
| legacy | 13.2336 | 0.5000 | 0.34453 |
| jhash | 15.9993 | 0.0292 | 0.00495 |

logging과 string은 같은 길이와 시드에서 같은 해시 코어를 사용하므로 품질 결과가 같았다. 두 경로와 jhash의 평균 변경 비트는 16에 가까웠고, legacy는 이 입력 조건에서 더 큰 편향을 보였다. jhash의 16·64바이트 최대 편향은 실험에서 사용한 보수적 99% 동시 오차 기준을 넘었다. 이는 시드와 표본을 바꿔 확인할 관측값이지, 이 한 번의 비교로 알고리즘 전체의 품질 순위를 정할 근거는 아니다. 여기서 다룬 것은 합성 입력 주변의 비트 확산이며 암호학적 안전성 평가는 아니다.

출력 충돌은 별도로 보았다. 서로 다른 키가 동일한 32비트 해시값을 만들면 출력 충돌이고, 서로 다른 해시값이라도 `hash & mask` 결과가 같으면 시작 버킷 충돌이다. 출력 공간을 균등하게 사용하는 이상적 모델에서 20만 개 입력의 출력 충돌 쌍 기댓값은 `n(n-1)/(2 × 2^32)`, 약 4.657쌍이다. 실제 구현의 0→2 정규화는 이 기준에 매우 작은 보정항을 더한다.

| 64바이트 random 입력 200,000개 | 출력 충돌 쌍 | 시작 버킷 충돌 쌍 |
| --- | ---: | ---: |
| logging | 5 | 304,510 |
| jhash | 5 | 305,516 |
| 이상적 균등 모델 | 약 4.657 | 약 305,174 |

시작 버킷은 65,536개이므로 평균적으로 버킷당 약 3.052개의 키가 배정된다. 버킷 충돌 쌍은 같은 버킷에 배정된 키가 `k`개일 때 `k(k-1)/2`를 더해 구했다. logging과 jhash 모두 이 조건에서 균등 모델에 가까운 값을 보였지만, 이것은 **삽입 전 시작 위치의 분포**이다. Robin Hood가 항목을 이동시킨 뒤 실제 탐색이 얼마나 길어지는지는 테이블에 넣어서 다시 확인해야 한다.

## 해시 계산 비용은 전체 조회 비용의 일부다

64바이트 random 입력에서 logging의 중앙값은 20.20 ns/hash, jhash는 19.85 ns/hash로 근접했다. string은 같은 코어를 사용하지만 길이를 구하는 작업까지 포함해 22.08 ns/hash였고, legacy는 40.70 ns/hash였다. logging과 string의 차이는 품질이 아니라 입력 처리 경로의 차이와 함께 읽어야 한다.

| 64바이트 random 입력 | 중앙값 ns/hash |
| --- | ---: |
| logging | 20.20 |
| string | 22.08 |
| legacy | 40.70 |
| jhash | 19.85 |

이 시간에는 함수 호출과 키 접근, 반복 루프, 반환값 정규화 등이 포함된다. 미리 생성한 키를 반복 처리한 배치 평균 비용이지, 해시 산술 연산만 분리한 시간은 아니다. 짧은 8·16바이트 입력에서는 jhash가 string보다 빨랐으며, string에는 `strlen()` 비용이 포함된다. 하드웨어 카운터 접근 제한으로 실제 CPU 사이클은 확보하지 못했으므로 시간에서 사이클을 환산해 결과로 제시하지 않는다.

## 테이블에 넣은 뒤에는 PSL과 탐색 횟수를 본다

Robin Hood 삽입이 끝나면 슬롯 하나에는 항목 하나만 남는다. 이 상태에서 슬롯의 중복 점유를 세는 대신, 각 항목이 home bucket에서 얼마나 멀리 이동했는지를 측정해야 한다. 테이블 크기를 `B`, 최종 위치를 `s`, 시작 위치를 `h`라 하면 이 구현의 PSL은 `(s - h + B) mod B`이다. 처음 위치에 저장된 항목의 PSL은 0이며, 성공 조회는 그 위치까지 PSL+1개의 슬롯을 확인한다.

테이블 실험은 logging과 jhash에 동일한 64바이트 키, 시드 설정과 삽입 순서를 적용했다. 용량은 262,144슬롯으로 미리 확보하고 점유율 25·50·70·75%를 비교했다. 여기서 시드 설정을 맞췄다는 것은 실험의 재현 조건을 맞췄다는 뜻이며, 두 해시의 시드 크기나 보안 성질이 같다는 뜻은 아니다. random 키는 무작위 hex 본문과 고유 접미사로, sequential 키는 공통 접두사와 순차 증가 접미사로 구성했다.

| random 키 점유율 | logging 평균 PSL | jhash 평균 PSL |
| --- | ---: | ---: |
| 25% | 0.167 | 0.168 |
| 50% | 0.501 | 0.504 |
| 70% | 1.184 | 1.165 |
| 75% | 1.515 | 1.487 |

두 해시는 점유율이 높아질수록 함께 더 긴 탐색 거리를 보였다. 차이가 큰 것은 해시 간 평균 PSL보다 테이블을 얼마나 채웠는지에 따른 변화였다. sequential 입력에서도 평균 PSL은 25%에서 0.164/0.173, 75%에서 1.486/1.520으로 비슷한 범위였다. 따라서 이번 입력에서는 어느 한 해시가 특정 점유율에서 탐색 거리를 크게 늘리는 현상은 관측되지 않았다.

### 75% 점유율에서 조회가 확인한 슬롯

random 키 196,608개를 넣었을 때 logging의 성공 조회는 평균 2.515개 슬롯을 확인했고, jhash는 2.487개였다. 평균 PSL에 1을 더한 값과 일치한다. 평균뿐 아니라 탐색 횟수의 상위 구간을 보아도 성공 조회 p99는 두 경로 모두 9개 슬롯이었다.

| 측정 항목 | logging | jhash |
| --- | ---: | ---: |
| 평균 PSL | 1.515 | 1.487 |
| PSL p99 / 최대 | 8 / 17 | 8 / 19 |
| 성공 조회 평균 확인 슬롯 | 2.515 | 2.487 |
| 실패 조회 평균 확인 슬롯 | 2.885 | 2.870 |
| 성공 조회 p99 확인 슬롯 | 9 | 9 |
| 실패 조회 p99 확인 슬롯 | 10 | 9 |
| 삽입당 평균 교환 횟수 | 0.672 | 0.650 |

실패 조회의 슬롯 수에는 실패를 결정한 빈 슬롯이나 PSL 조기 종료 슬롯도 포함한다. p99 역시 실행시간의 p99가 아니라 **확인한 슬롯 수 또는 PSL의 p99**이다. 이 구분이 있어야 탐색 거리의 분포를 곧바로 지연시간 분포처럼 해석하지 않는다.

### 실제 API 시간에서도 뚜렷한 일방적 우위는 없었다

탐색 비용이 비슷한 두 경로는 삽입과 성공 조회 시간도 근접했다. logging의 삽입 중앙값은 43.59 ns/op, jhash는 45.50 ns/op였고, 성공 조회는 각각 205.09와 206.67 ns/op였다. 실패 조회에서는 jhash가 더 짧은 시간을 보였다. 한 연산의 작은 차이를 전체 테이블의 일관된 우위로 확대하기보다, 조회 종류에 따라 차이가 달라진다는 결과로 읽는 것이 맞다.

| 연산 | logging 중앙값 ns/op | jhash 중앙값 ns/op |
| --- | ---: | ---: |
| 삽입 | 43.59 | 45.50 |
| 성공 조회 | 205.09 | 206.67 |
| 실패 조회 | 96.11 | 90.41 |

시간은 계수기를 넣지 않은 원본 구현에서 5회 측정한 중앙값이다. 탐색 횟수와 교환 횟수는 별도의 계수용 빌드에서 측정해 시간 측정과 분리했다. 삽입 시간은 빈 테이블을 목표 점유율까지 채우는 전체 평균이며, 이미 75%가 찬 테이블에 한 건을 추가하는 비용이 아니다. 생성·메모리 할당·리사이징은 측정 구간에서 제외했고, 성공 조회는 저장 키와 별도로 복사한 키 버퍼를 사용했다. 따라서 이 결과는 고정 용량의 합성 입력 실험이며, 실제 로그의 hot-key 분포나 삭제·재삽입 반복 비용까지 포함한 결과는 아니다.

## 정리

이번 실험에서 64바이트 logging 경로는 jhash와 비슷한 해시 계산 비용을 보였고, 같은 Robin Hood 테이블에 적용했을 때도 평균 탐색 거리와 확인 슬롯 수가 근접했다. 특히 75% 점유율에서 성공 조회는 두 경로 모두 평균 약 2.5개 슬롯을 확인했다. 해시의 출력 분포를 보는 단계에서 그치지 않고 실제 배치 이후의 탐색까지 확인했다는 데 의미가 있다.

SHashTable을 이해하는 핵심은 세 단계를 구분하는 것이다. 해시 함수가 시작 위치를 정하고, Robin Hood 삽입이 충돌 이후의 배치를 만들며, 조회가 그 배치와 PSL을 이용해 탐색을 수행한다. 다음 측정에서는 다른 시드와 실제 로그 키 분포를 적용하고 삭제·재삽입과 리사이징을 포함해, 이번 고정 용량 결과가 어떤 사용 조건에서도 유지되는지 확인할 수 있다.

### 구현과 측정 기준

아키텍처 설명은 `shash.h`, `shash.c`, `hashtable.h`, `hashtable.c`를 기준으로 했다. 측정 방법은 `tests/README.md`, `run_hash_tests.py`, `run_robin_hood_tests.py`의 구분을 따랐으며, 표의 수치는 제공된 실험 요약에서 인용했다. 이 글을 작성하면서 벤치마크를 새로 실행한 것은 아니다. 요약에 빠진 CPU 모델·컴파일 옵션·실행별 원시 값은 추정해 채우지 않았다.
